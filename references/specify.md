# 固化需求基线 / Specify The Requirement Baseline

已完成准入和澄清后加载。默认权威是一份统一 PRD 及其稳定 ID 索引；只有规模、反复变更、
受控多投影或强审计需要时才增加独立 Product Truth。

## 输出语言与阅读合同 / Output Language And Reading Contract

文档语言优先采用用户明确要求；未指定时继承本次任务起始时的主要语言，并贯穿后续阶段。“继续”或
“下一步”不重置语言，只有用户明确切换时才更新。标题、正文、表头、澄清、测试叙述和图中节点统一；
全英文交付必须使用英文标题、表头、提问、页面文案、图节点、测试和门禁诊断，不得残留中文模板骨架；
中文交付使用“前提/当/则/并且”等本地语言，不把 Given/When/Then、draft、pending → resolved 或
lastCursor 当正文标签。稳定 ID、代码、API/字段名、Schema 关键字、公式和机器枚举不翻译；这些原值
出现在人类正文、表格或图中时，必须先给人类标签再映射机器值，如“草稿（`draft`）”“待处理
（`pending`）→ 已解决（`resolved`）/申诉中（`appealing`）”“同步游标（`lastCursor`）”“未知来源
（`unknown_source`）”。来源标题可保留原文，但要用文档语言解释其含义。
只有用户明确要求才生成双语。文档头机器元数据（frontmatter）声明 `document_language`、
`language_source` 和 `bilingual`。中英混合输入未指定输出语言时取主要交流语言，不把每段分别翻译成
双语。机器侧车交付时另附同语言的人类可读摘要；门禁使用 `--language auto|zh-CN|en-US`，`auto`
先读 `document_language`，确保诊断也跟随文档语言。

问题简报、方案草图、需求澄清简报和统一 PRD 的权威形态是 Markdown + frontmatter；DOCX/PDF 只允许作为基线后的分发副本，不得反向覆盖权威基线。无 frontmatter 或仅有分发件时，门禁必须阻断而不是猜测元数据。分发时必须先从权威 Markdown 生成去除 frontmatter 与 `ADS:*` 编辑注释的人类 Markdown，再转换 DOCX/PDF、渲染检查版式；不得把权威文件直接交给只做纯文本复制的转换器。可用 `project-human` 与 `check-distribution` 检查投影边界，PDF 仍以实际渲染为准。

一份 PRD 采用渐进阅读：30秒摘要与角色阅读入口 → 业务背景与旅程 → 模块完整纵切 → 横切合同
→ 工程附录的机器投影。附录引用相同 ID，不重复改写业务含义。前端、后端、QA或 Coding Agent
应能通过一个模块纵切和具名索引完成工作，不必跨章拼规则或再次询问缺失行为。

## Human-First 编辑规则 / Human-First Editing Rules

统一 PRD 分两层：**正文面向人**（第 0—10 章，顺序可读），**工程附录面向机器与 AI Coding**
（第四部分，精确投影）。生成和维护统一 PRD（`references/templates/unified-requirement-prd-template.md`，
模板内 `ADS-EDITING-RULES` 注释块与本节互为权威，冲突时以本节为准）时必须执行：

如果用户明确要求 PRD 且交付层级为 L2/L3，实施步骤卡、原型评审工作台和专项评审说明都不能替代这份统一 PRD。交付前必须运行 PRD 门禁：未知业务决策可以让状态保持 `BLOCKED`，但已知的来源、范围、角色旅程、页面合同、字段/规则/状态、API/事件语义、机器验收和双向追溯不能因“先评审”而省略。专项说明只能标为“补充件”，并引用统一 PRD 的版本/hash 与稳定 ID。

1. **一事一处**：每条事实（字段含义、业务规则、指标口径、权限、状态转换、错误处理）
   只有一个权威位置；他处只引用其稳定 ID，不复制、不改写。发现同一事实写在两处时，
   保留读者最先需要的那一处，其余改为 ID 引用。
2. **正文/附录边界**：正文用业务语言叙述，稳定 ID 在事实首次出现处就近标注，不堆全局
   索引表；字段字典、规则与状态机明细、API/事件契约、AI 合同、权限审计 NFR 矩阵、
   机器可读验收、双向追溯等机器表格一律放工程附录。附录不引入正文不存在的业务语义；
   两处冲突时以正文为准，且必须在同一 `CHG-*` 中同步附录
   （`governance.projection_policy=update_in_same_change`）。
3. **角色任务入口**：第 0 章必须给出角色/任务阅读入口表，声明业务/客户、产品/设计、前端、
   后端/架构、测试/验收和 Coding Agent 要完成的真实任务、先读的语义锚点/模块以及稳定 ID 和完成标准。
   不得只写易漂移的“第几章”；章节合并、拆分或重编号后，稳定 ID/语义锚点仍须可定位。
4. **章节密度控制**：正文二级章节（`##`）不超过 12 个。超出时先按用户路径合并相邻
   章节（如数据流转并入业务流程、指标口径并入非功能），再把机器索引下沉到附录；
   不得在正文平铺新章节，也不得把 0.x 等文档控制小节提升为与部分标题同级的章节。
5. **先业务闭环后工程投影**：章节顺序固定为 文档控制与 30 秒摘要 → 背景目标 → 范围 →
   角色与数据边界 → 端到端旅程 → 业务流程与状态 → 分模块纵切 → 横切约束与验收 →
   工程附录。读者必须先能走完用户路径和业务闭环，才进入模块纵切，最后才是机器投影；
   禁止把机器契约插入正文打断阅读。

## 需求卡升级规则 / Requirement Card Escalation

需求卡只适用于单角色、可逆、局部变化。保留目标、范围、故事、主/恢复流程、规则权限、AC和
未知项，再按需启用 `ui`、`stateful`、`data_submission`、`integration`、`batch_io`、`high_risk`。
已启用切面必须完整规格化或登记责任未知项，未启用切面不增加 Token 成本。

出现任一情况即升级为统一 PRD：跨角色交接、跨模块/系统边、实质状态机、数据上报/统计口径、
批量导入导出、审批审计、外部集成、金钱/隐私/监管、不可逆写入、迁移或版本兼容。
数据上报默认至少 L2，因为来源映射、校验、提交状态、重试、幂等、审计、时效和对账涉及多角色。

## 来源模型 / Source Model

`REQ-*` 是范围和追溯权威。启用 Product Truth 时，schema 是机器合同，统一 PRD 仍是人类阅读
和批准的基线投影。

```text
SRC → REQ → MOD/FLOW → VIEW/REG → ACT/FLD/RULE/STATE/API
          │                                      │
          └────────────────────→ AC → TEST/ARUN → EVD
          ↑                                      │
          └──────────────── CHG / DEFECT ←────────┘
```

| 对象 | 前缀 |
|---|---|
| 来源/断言/决策/未知/冲突 | `SRC/AST/DEC/UNK/CFL` |
| 需求/能力/评审 | `REQ/FEAT/REV` |
| 角色/模块/实体/字段 | `ROLE/MOD/ENT/FLD` |
| 流程/页面/区域/动作 | `FLOW/VIEW/REG/ACT` |
| 状态机/状态/规则/事件/集成/API | `STM/STATE/RULE/EVT/INT/API` |
| 验收/测试/执行/缺陷/证据/变更 | `AC/TEST/ARUN/DEFECT/EVD/CHG` |

ID 永久稳定。语义未变只改名称时不换 ID；拆分、合并、弃用或移除通过 Change Package 保存
`deprecated_ids` 和 `replacement_map`。每个已基线 `REQ-*` 绑定来源、目标、行为、验收、责任人、
优先级、阶段和版本。`FEAT-*` 可用于兼容分组，但不能代替需求记录。延期、拒绝、被替代、未知、
不适用和范围外均显式保留。

## 模块交付纵切 / Module Delivery Slice

按用户/领域结果分模块，不按前端/后端/数据库分层。每个范围内模块就近包含：

1. 目标、角色、入口和成功出口；
2. 主流程和异常流程；
3. 页面/区域和数据展示；
4. 字段、字典、来源、可编辑性和敏感性；
5. 动作、守卫、可见结果、命令/领域结果和失败结果；
6. 状态机、规则、事件、权限、审计和补偿；
7. 集成、时效、幂等、对账和依赖责任人；
8. 验收路径、证据、模块指标/数据质量和未知项。

正文按复杂度提供最小的人类可读图，不以机器表格或长段落代替：跨页面/模块/角色且有三步以上依赖的
核心链路画流程图；存在三个以上业务状态、守卫、分支、撤销或回退时画状态转换图；存在跨系统、
汇聚/转换、AI处理、正反向同步或对账时画数据流/血缘图。简单单页 CRUD 不机械加图。图中节点使用
文档语言并保留稳定 ID，图后就近引用详细规则，不把整份 PRD复制进图中。

横切章节只放真正共享的合同；附录承载面向机器的精确投影（边界见 Human-First 编辑规则）。
统一 PRD、工程附录和可选 Product Truth 不得互相矛盾，也不得发明基线不存在的行为。

### 指标澄清合同 / Metric Clarification Contract

页面、报表、排序、预警或验收一旦依赖数量、比率、时长、金额、排名或趋势，每个业务含义分配唯一 `METRIC-*`，明确对象、公式/分子分母、时间窗/时区、过滤状态、去重键、权威源、刷新时效、零值/空值、单位精度和口径版本；同一 ID 只能重复展示同一含义。任一会改变实现或验收的口径缺失时，在规格定稿或生成评审态前按依赖批量反问；暂时无人确认则登记 `UNK-METRIC-*`（责任人、影响、`blocks_stage`、回退），可交阻塞草稿，不得标成“已确认”或声明基线/开发就绪。

## 页面合同 / Page Contract

每个实施相关页面必须声明：

- `VIEW-*`、所属模块、可见角色和页面 `surfaces`；
- `REG-*` 区域、重复记录规则、字段、动作和查询来源；
- 默认（`default`）、空数据（`empty`）、加载中（`loading`）、错误（`error`）、部分/陈旧（`partial/stale`）、成功（`success`），以及该页面实际可到达的权限状态；
- 弹窗/抽屉链，长数据、窄屏、打印/导出行为（适用时）；
- 流程、动作、状态、API和 AC 链接。

只写“见原型”或只有组件清单均不合格。

## 动作合同 / Action Contract

每个实质 `ACT-*` 至少包含：

- 触发器、允许角色/状态、守卫和二次确认；
- 执行反馈和持久可见结果；
- 适用的命令/API；
- 领域结果、下一状态、事件、审计和幂等；
- 校验、权限、依赖、重复、超时、陈旧写入的失败及恢复；
- `AC-*` 引用。

状态变化型核心命令不能只显示 Toast。

## 流程合同 / Flow Contract

每个 `FLOW-*` 声明角色、模块、起始条件、步骤、每步可见/领域结果、异常分支、补偿、最终证据和 AC。
步骤间使用 `EDGE-*` 表达 start/next/branch/parallel/join/return/error/compensate/finish，不把并行、汇聚、
退回压成一个“下一步”字段。跨模块流程还要声明源/目标对象、字段映射、状态责任人、生产者/消费者、
重试和对账。

### 核心实施步骤合同 / Implementation Step Contract

流程中的每个持久写入、状态转换、指标重算、责任交接或跨系统边，必须分配稳定 `STEP-*`。PRD 在步骤
所属模块纵切内就近给出完整实施卡，不能要求前端、后端、测试或 Coding Agent 横跨总流程、模块章节和
附录自行拼接。每张卡至少包含：

- 业务目的、可见入口、允许角色/数据范围及入口/动作权限表现；
- 输入对象、版本、字段、来源、权威源、时效与匹配键；差异确认后明确回写哪个权威对象，或只保存本次快照；
- 校验/计算/比较/合并/去重/覆盖的处理口径，适用公式明确分子分母、时间窗、状态、零值和格式；企业、人员、车辆、证件、明细等同时明确计数单位；
- 前置守卫、前状态→后状态、非法转换结果、用户可见反馈与持久领域结果；
- 事件/审计/日志及其行粒度，成功、失败、部分成功的数量如何归集；下一责任方、输出/消费者与下一可达入口；
- 校验失败、权限拒绝、超时、重复、部分成功、版本陈旧的恢复、补偿、重试、幂等和对账；
- `REQ/FLOW/VIEW/ACT/RULE/STATE/API/EVT/AC/source_ref`，以及已确认/建议/未知/观察缺陷。

共用事实只定义一次；评审原型、结构化 handoff 和角色镜头引用相同 `STEP-*`。普通只读字段无需强行
拆卡，但任何会影响实现或验收的缺项必须明确为 `GAP/UNK/REV`，不得靠口头评审补全后仍宣称开发就绪。
交互账本、评审工作台和 handoff 只能投影同一 PRD 基线，不能反向授权 PRD 中不存在的业务动作、验收
或规则。`implementation_step_refs` 一旦声明，必须解析到 PRD 中完整的 `STEP-*` 卡；开发就绪时不得漏包。

## 状态、权限与数据 / State, Permission, And Data

- 聚合或所属系统是状态权威；后端守卫业务状态，UI隐藏不等于授权；
- 页面入口权限不足：菜单和路由入口不可见，直接 URL/API 仍返回 403 或产品约定的拒绝结果；普通路径不展示页面内无权态；
- 页面可见但数据范围为空：展示空数据/范围内无数据（`empty/no_data_in_scope`），不得误写成无权限（`no_permission`）；
- 动作/组件/字段权限不足：分别声明隐藏、禁用、只读或脱敏及服务端守卫；只有深链、权限在会话中撤销、
  或页面内独立区域不可用等真实可达场景，才展示局部/页面无权限（`no_permission`）；
- 数据范围按需精确到租户、组织、部门、所有者、合作方、记录、字段、目的和时间；
- 金钱、安全、监管、敏感导出和有后果的 AI 写回必须有责任人和审计；
- 数据源声明所有者、时效、质量、权限、保留/删除/导出及失败行为。

## 非功能要求档案 / NFR Profiles

只加载适用档案，不强行填写任意数字。

| 档案 | 最低关注点 |
|---|---|
| standard enterprise | 可用性、性能、审计、备份、支持 |
| multi-tenant SaaS | 隔离、配额、导出、租户生命周期、资源争用 |
| realtime | 延迟、顺序、重连、重复、时钟、降级 |
| data product | 时效、血缘、质量、成本、回填、语义一致 |
| AI core | 评测、安全、上下文、工具范围、回退、回滚、可观测 |
| regulated/high risk | 权威、人工闸、不可变证据、恢复、事故责任人 |

## 基线门禁 / Baseline Gate

以下任一情况存在时不能声明需求基线完成：

- 主要角色无法走完任务；
- 动作没有可见结果或领域结果；
- 状态转换没有责任人、守卫或事件；
- 跨模块交接没有失败和对账；
- 字段没有来源、含义或可编辑性；
- P0 断言仍为无责任人确认的推断；
- 已发布的模块/流程/页面/动作/字段/规则/API/AC 没有绑定 REQ；
- 验收路径无法产生要求的证据。

## 不新增第二份 PRD 的 AI Coding 交接

统一 PRD 同时是人类评审路径和业务实施合同；机器表格/YAML只是同一基线的投影。L2以上接收方
必须能推导：角色与数据范围、主/异常流程和恢复；页面区域、字段/控件/校验和可见状态；动作守卫、
领域结果、状态/事件/审计/幂等；业务 API/事件输入输出、错误、兼容和对账；正反 AC、夹具/证据、
反向追溯；禁止推断和开放决策清单。

框架、数据库 DDL、仓库结构和部署拓扑仍由工程团队决定，除非互操作、合规或验收让其成为业务合同。
缺少工程基线时，模块规格可以完成，但整体只能报告 handoff GAP，不能宣称开发就绪 PASS。


人类评审原型按旅程、当前 `STEP-*`、页面落点和前端/后端/测试角色工作包投影，不复制 PRD；Coding
Agent 读取结构化 handoff、实施步骤引用、稳定 ID 切片和工程基线。评审完成前执行无讲解冷读：产品能
复述目标/范围/决定/下一责任方，前端能复述入口/控件/状态/反馈，后端能复述权威源/守卫/领域结果/
恢复，测试能复述夹具/正反边界/双结果/证据，Coding Agent 能从 handoff 找到同一 STEP 与 AC。任何
角色仍需猜测核心语义时，登记 GAP/UNK 并阻断对应阶段，不能靠原作者口头补充后宣称开发就绪。
高风险 `RULE-*` 绑定权威 `SRC-*`、已批 `DEC-*` 或具名 `ASSUMPTION-*`。AI行为还声明输入输出、
模型/Prompt/工具版本、人工闸、回退、评测和可观测；血缘行为声明来源、转换、责任人和变更影响。
