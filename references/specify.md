# 最小充分业务规格

补清业务选择歧义，技术选择留研发。旧单缺值只决定历史读取方式；新单能否留空，看当前录入规则。未定时先交付已明确的分支。

## 沿实际任务组织

小改回填原处。工作发生在原表、邮件或线下时，沿用该载体，写清结果交给谁、拿来做什么。正式PRD先述目标、范围、角色、主链和通用约定，再按页面/对象展开。指定单册时精确机器规则在同册尾部，不能依赖另一册才能开发；交付形式遵从用户约定。

配置组合或下游消费仍有歧义时，可查[配置到消费](../examples/configuration-to-consumption.md)；需要写法参照时取[工单样例](../examples/medium-review-handoff/requirement.md)、[需求卡](templates/prd-light-template.md)或[PRD骨架](templates/unified-requirement-prd-template.md)。已有材料足够时无需补读范例；问题、方案与澄清可同册回填。

1. 从原始决定写清一个任务：谁对哪个对象，在什么状态/条件下操作，成功改变什么，拒绝保留什么，之后从哪继续。涉及配置、执行或发布时区分实际对象，不为套示例补出不存在的阶段。未定分支就地标出，不能靠状态名推断政策；例如尚未生效不因“不生效”就属于已过期。
2. 同一对象字段只定义一次，按相关新增/编辑/列表/详情场景对照含义、来源、类型/控件、必填、默认、校验与可改条件；不补齐无关CRUD。分期差异写在该字段和动作原处，后期能力不提前解锁或阻断本期。派生列说明生产者与消费者，不补手填。节点及异构子类型就地分表，位置对应真实页面，见[实例](../examples/consolidate-existing-module.md#actual-config-objects)。
3. 界面和正文使用该领域通用词及同一业务名称；内部枚举不代替用户文案，同词不同义先区分对象和结果，不能机械替换。动作归属页面任务，区分位置、作用、条件/权限、结果及恢复；按阅读需要合并列。把该动作的状态、数据和通知副作用一起写清，不让开发从其他章节猜。图补结构，文字保留硬条件。
4. 呈现方式由内容决定：需要横向比较的参数、状态或规则保留表格；解释配置和业务过程时，写清操作者从哪里开始、如何操作及结果。不能按列数或字数阈值，把表头标签机械拼成正文；改写后逐项核对原条件、数值、权限和例外。截图靠近对应界面，图讲主链，文字讲实现条件，不能用截图代替说明。列表、详情、配置和消费者的同一值应同源；同一动作多入口分别核对，不能以单条代替批量。
5. 验收用业务标题，写前提、操作、预期结果；ID辅助引用。也可用“用例／前置数据与操作／页面结果／业务结果”四列表，反例独立成行，未执行不填已通过。共用规则一次定义，使用处标范围、差异和定位。读完模块须能确定输入、结果并造数，不能跨处猜关键步骤。稳定ID不因章节改名重编。

## 对选定行为展开规则与验收

| 内容 | 写清什么；用什么反例检验 |
|---|---|
| 状态/审批 | 分别核对对象与触发事件的变化及不变项、守卫和副作用；审核仅为前提时不等于发布，已授权自动发布不反改人工 |
| 退回/拒绝/失败 | 谁可改什么、从哪恢复、旧对象保留什么；失败不能只剩提示 |
| 指标/统计 | 新定义写对象、粒度/行数、公式/分母、时间/时区、过滤去重、来源、空零和时效；引用既有指标则定位定义并核对实际消费。演示参数不升级为正式政策，列数正确不证明粒度正确 |
| 权限/数据 | 多角色动作不同，在本模块或共用权限矩阵对照“角色 × 动作”，仅在有差异的格子注明对象范围和状态。写清已确认、初始建议和待定项，模块引用对应行。单一角色一句话即可。系统执行、消费身份另按有效约定核对。 |
| 配置/旧对象 | 配置输入来源、提供者、时点及缺失行为；变更何时生效、旧实例如何处理 |
| 批量/异步/外部系统 | 提交前拒绝、调用已发出、明确失败、结果未知及正式成功凭据；不完整响应如何查询/对账；重试不得假定上次未写入 |
| 高后果AI写入 | 可信来源、可操作范围、确认/回退、拒绝；不越过用户授权 |

上表只展开当前约定的行为。写首版前先问：删去这句，开发是否会做错本次业务结果？可直接沿用的规范只引用，不附带新增实时预览、字段限制或旧数据迁移等无依据的要求。访谈中的岗位称谓先对照已有角色，职责描述不能自行授予新权限。新增人工步骤、独立机制或可配置项前，判断其对应的已知结果、现有能力能否承担，以及操作者是否确有选择；在原处说明实质取舍，可引用已有依据，不为每个字段填写必要性表。对标产品提供可比较的做法，有对标不证明适用，无对标也不证明无需求。必要的权限、幂等和数据保护通常由系统执行，不因此增加填写、证明或确认；确需人判断的政策与例外仍由人处理。普通提交失败可由本页保留输入、手动重试和离页提醒处理；只有确需断网持续作业、重启保留或自动同步时才设计相应恢复机制。固定规则不自动变配置，未定政策不藏进默认值。需要参照时看[三个机制取舍案例](../examples/configuration-to-consumption.md)，无需另交机制审批表。

“相同、有效、成功、完成”就地写字段及排除项。区分0、空、未采集、无权、失败和陈旧；来源有效不等于内容真实，相关性不是授权，置信度不是完成率。非功能目标写负载/资源/计时/失败统计条件；缺依据保留待决，不臆造SLA或把目标写成实测。

按对象、条件和有效版本归并正文、图、样例与原型，回填原处。参照[归并与分期示例](../examples/consolidate-existing-module.md)，保留历史/当前、配置/运行及不同用途的合法差异。示例、领域包不是项目授权，未决仅限制依赖它的规格结论，不自动生成运行限制。

## 接收者冷读与行为验证

复杂交接由独立接收者先只看约定交付包，给出自己理解的操作过程和一个验收例子，再查原始来源；来源本属于交付包时保留。按约定模块说明实际使用者从哪里开始、输入什么、发生什么及失败后怎么继续；需要补猜的关键业务选择定位到原句，不能自行补齐后判通过。接收者先留下首次判断，再看作者解释、测试脚本或旧结论。文档只写“按角色控制”时，即使原型能点，也应指出哪些动作与数据范围仍无实施依据。逐句通顺、标题、截图和“已读”记录都不能代替接收理解。

要求模块独立可读时，关键业务步骤应在本模块可确定；清楚定位的共用定义可引用，不能靠全册拼接或作者口头补课。接收者无法确定的业务选择要作为该模块缺口，修后再读，不能用“建议阅读附录”替代完成。可理解性、来源忠实性、实际操作和视觉检查分别报告；一个维度通过不补齐另一个。AI接收不是真人验收，作者自检不是独立冷读。

先想貌似合理的错误实现，用可区分的数据检验。负例只改待测条件，核对拒绝原因及副作用。配置从真实入口→保存→重开→执行→消费→修改→旧实例，按实际环节走；非默认值和边界应改变结果。已有导入导出才查保真，预置样例或隐藏函数不证明用户可配置。

首次遗漏、修订回退和待决业务分别记录。文档与原型各自核对业务来源。

交给开发/Coding Agent 时按[交接边界](context.md#给研发测试与-coding-agent-的交接)引用本次范围及原文；复杂交接才索引起点、依赖和验收。已有有效决定直接继承，工程约定缺失且影响实现才澄清。

复核最终正文、截图、状态及验收；Word/PDF须渲染，Markdown不证明版式。小改不强制全角色冷读；静态、模拟、浏览器、后端及签署分列。

## 可选机器声明

日常不强制元数据或台账；检查见[工具](stages.md)，草稿用specify，基线用baseline。DEC/UNK可在正文维护；关闭未知须有resolution_ref/source_refs，风险接受保留授权范围。semantic_reviews按Schema记录并复用ARUN/EVD，不把not_run改pass。

GAP需判明缺决定、合理差异或误报，不为变绿编造政策。机器契约联调可用[check-examples](stages.md#契约样例校验)，不替代语义和运行验证。

用例区分业务结果、允许的实现投影和观察层级；技术选择不豁免重复写入，见[异步反例](../examples/configuration-to-consumption.md#异步写入与真实接收)。
