# 判断、探索与澄清

先辨认用户给的是问题、目标、候选方案、批准变更还是观察。对明确授权的小改继承决定；对模糊机会，找当前真正需要判断的事项。

## 从证据推进

观察发生在谁、什么场景、什么对象上；区分购买者、管理者与实际使用者。把可能原因当作假设，找能够改变方案选择的证据。局部观察要推广成收益判断时，核对样本是否代表目标人群、是否有其他原因，以及是否把成本转给其他角色；仅在会改变决定时补查。比较有实质差异的选择以及维持现状的代价；在形成下一决定所需信息足够时停止。

诊断关系是“观察→可能原因→会改变选择的证据→最小验证→推荐决定”。直接写入现有 problem brief 或 solution sketch，不生成一份额外诊断报告。可复用 [problem-brief-template.md](templates/problem-brief-template.md) 和 [solution-sketch-template.md](templates/solution-sketch-template.md)，按当前目标裁剪。

战略、系统、行为和反方视角是可选思考角度，不是四轮问卷。只描述有依据的动机与激励，不给人做心理诊断。比较方案时把用户要做的动作和系统能承担的工作分开；删除候选步骤后仍能达到已知结果，就先采用较少维护和交接的做法。并非把所有判断自动化，实际授权和业务制度仍有效。

## 决定与未知

先查直接相关的存量能力、规则和开放问题；已有答案且适用就继承。优先问会改变范围、权威、业务结果或验收的主问题；少量独立小项可合并一轮，不依赖尚未得到的答案。其他工作继续，轮数不证明充分。

“是否、多少、如何”也可能是未决选择；不能因未写“待确认”或分诊漏报当作已定。区分业务提问、界面文案和已有答案；[共性模式](patterns/common-requirement-patterns.yaml)只提示适用且未回答的问题。

澄清前核实问题前提与现有能力。只有答案会改变业务结果、范围或决定权，且不能据现有授权处理时才问；合理工程选择自行判断，不让用户替模型选技术机制。用具体场景、已有事实和不同选择的后果提问，避免把假设包装成必须二选一的政策。推荐有依据但不冒充决定；回答就地记入原产物，不另交问答日志。

用户最新有效决定在授权主题内覆盖旧内容。未合入正式文档不意味着需要重新批准。合同、法规或系统权威是否适用须核实，不能按文件新旧或长度自动排序。

未知注明影响与决定时点，已有负责人直接沿用；没有负责人不虚构。缺决定限制本次方案或交付中依赖它的部分，不据此设计禁用按钮、冻结账号或发布拦截。已存在的业务限制仍按其授权规则执行；需要正式接受风险时不能由模型代签。

退路不得选定未决政策。例如补考取值未定，暂停依赖该选择的结论或保留待决分支；不能将“取最新”标成保守默认。晚到数据、冻结、权限例外和历史迁移同理。

## 暂缓、不做与收敛

建议暂缓、不做、缩范围记在当前产物或 DEC 中，标记 proposed；明确获权后才 confirmed。记录理由、证据、适用范围及复议条件。无正式 REQ 时不为记录建议强制准入。

分析任务可以在给出有依据的建议后完成；需求是否取消、外部承诺是否撤回、系统是否停止是另外的授权与执行。已有用户决定不重复问。状态细则见 [lifecycle.md](lifecycle.md)。

停止依据当前目标所需的决定，不是先关闭未来所有 P0 再允许得出“暂缓”。若当前成功就是确认缺少价值证据，应交付最小验证、责任/复议条件及未定范围，保留实施缺口；检查时明确 `--stage frame` 或 `--stage explore`。

当前决定足够明确后，自动回到用户要的 PRD/原型/变更交付。用户要求完整结果时不把澄清清单当终点。分析可以止于下一决定；可交开发的产品包则须在所交范围内明确用户任务、拒绝/恢复与未决执行边界，并写回规格，不以“无需再问”代替可实现。按[产品交付出口](context.md#产品交付出口)收口，不询问未受影响的未来政策。
