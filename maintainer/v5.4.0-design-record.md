# v5.4.0 设计记录：阶段工作站，而非更重的全链路框架

## 决策

在 5.3.3 的需求管理内核上增加九个“可进入/可停止/可续接”的工作站，但不升级为 v6，不增加第二套生命周期、第二套 CLI 或第二套门禁状态。

## 吸收的专家实践

- `frame → explore → intake → clarify → specify → review → baseline → change → acceptance` 的阶段矩阵。
- 问题简报、方案草图、假设、决策与需求简报作为可交接产物。
- 角色可以在所需阶段进入，目标产物完成即可离开。
- 跨会话续接必须保存前序产物和开放线程。

## 未直接照搬的部分及原因

1. 不用关键词脚本推断自然语言：它会把“不要写 PRD，只做澄清”误路由到 specify，也难以稳定支持多语言和否定语义。
2. 不要求每次运行 stage router：模型负责语义，工具只做确定性核验，避免新增 shell/转义/Token 成本。
3. 不增加独立 `stage_gate.py + stage_router.py`：合并为一个 `stage_contract.py`，并从现有公共 CLI 调用。
4. 不发明 `COMPLETE/NOT_READY`：继续使用 `PASS / REVIEW_COMPLETE_WITH_GAPS / BLOCKED_BY_P0_UNKNOWN / BLOCKED`。
5. 不为每阶段强制一份文件：frame/explore/clarify 默认各一份；假设和决策仅在治理需要时拆侧车；baseline 复用统一规格。
6. 不让 artifact resume 替代大项目 execution-state：前者保证交接完整性，后者保存 ID 切片、预算和运行检查点。
7. 不在 frame/explore 提前分配正式需求 ID：正式治理从 intake 开始，避免把脑暴选项误当批准需求。

## 关键不变量

- 一份统一 PRD/需求卡仍是人类与 Coding Agent 共用基线；Product Truth 严格按需。
- 用户语言、来源权威、稳定 ID、禁止推断、双向追溯和真实验收边界不回退。
- 任何角色都能从现有证据进入，但 review/baseline/change/acceptance 不得在缺少可消费规格时凭空继续。
- 早期假设是 GAP，不自动成为 P0；P0 只阻断已经到达且受影响的正式阶段。
- 静态门禁不证明业务正确、实现完成、浏览器行为或客户签署。

## 文件与运行成本

- 新增一个阶段参考、一个合并脚本、两个 schema、五个模板和两个聚合回归文件；不增加碎片夹具。
- 维护设计记录只在发布保障时读取，不进入普通项目上下文。
- 冻结巨型 `quality_gate.py` 的新功能增长；早期工作站语义集中在 `stage_contract.py`，公共 CLI 只路由，不复制规则。
- Schema 版本按结构演进，不为追随 Skill 版本机械批量改号；只有新增 intake 合同使用 5.4.0。
- 仓库发布文件必须 `< 200`；第三方运行包使用 allowlist，`maintainer/` 不随普通用户运行时下发。

## 发布前案例与模型证据边界

- 15 个固定 GitHub 案例用于验证跨领域需求形态，7 行业保障组合用于验证阶段与角色覆盖；两者共同提供广度证据，但不等同于所有行业已经获得领域专家签署。
- 15 个案例各绑定一个“一句话需求”生命周期探针，并覆盖全部九阶段。`review / baseline / change / acceptance` 缺少前序证据时，正确行为是阻断并返回最小前置材料，而不是伪造产物。
- 下一轮真实快照优先候选为 OpenAI Codex、Qwen Code、ERPNext、DataHub、OpenEMR 与 Keycloak，分别补齐 AI Agent 协作、制造 ERP、数据治理、医疗与 IAM 场景；只有完成固定提交、来源路径、义务与运行证据后才能进入正式案例目录。
- Grok-1 主要是模型权重与推理实现，不直接代表需求生命周期或 Agent 工作流，不能为了品牌覆盖强行纳入。
- 跨模型测试必须记录真实 `provider / model_id / client_version / settings / run_at / output_ref`；生成测试包不等于模型已经通过，禁止使用共享、泄露或来源不明的凭据。

## Claude 系统测评的处置

本轮接受并落地：

- `review-record` 增加 `architecture / delivery / cross_functional` 类型、`required_review_types` 和逐角色 `sign_offs`；完成态不再只凭“没有 finding”通过。
- 新增“需求交付/技术负责人”使用者角色和离线需求池汇总，汇总优先级、复杂度带、依赖与迭代归属，但不接管 Sprint、人员、工期和容量决策。
- 在既有工具适配页增加 Jira/Linear/Azure DevOps/TAPD/禅道的索引映射，外部状态只写 `external_milestones`，不能覆盖统一需求基线。
- 独立区分 `architecture` 与 `engineering` 评审；补充紧急变更的临时授权、最小止损、回滚与补审规则；明确 Skill 使用者角色与 PRD `ROLE-*` 业务角色不是同一概念。

明确不扩张：

- 不增加 launch/monitor/operations 第十阶段。验收结论交给外部发布系统，线上反馈以新 `SRC-*` 回到 intake，或对既有基线创建 `CHG-*`。这是需求闭环交接，不是研发/运营管理。
- 暂不增加独立 ADR 模板；架构签署和决策继续复用 `decision-record` 与 review sign-off，避免文件膨胀。
- 暂不把 junior escalation、双语一致性或到期提醒扩成全局重型对象；先通过责任边界、P0 `blocks_stage` 和结构化评审阻断，后续只在真实逃逸案例证明需要时升级。

模型越强，越要删减“教模型如何思考”的重复 prose；稳定 ID、共享状态、证据、领域不变量和确定性门禁则继续保留。后续用目标模型对“完整段落 vs 两行锚点+门禁”做 A/B，行为无差异的推理提示删除，不凭厂商宣传机械瘦身。

## Kimi K3 受控复测与成本结论

- 仅使用本机 Kimi Code 的官方 OAuth 会话和运行时返回的 `kimi-code/k3`；用户在对话中提供的 Token 未使用、未写入任何文件，也不作为证据。
- 仓库工作副本首次抽测 frame / explore / intake：三个阶段的行为和独立门禁均通过，但 intake 约 424 秒、响应约 60 KB，说明“产物正确”不能掩盖加载与分析成本失控。
- 改用 101 文件 allowlist 运行包，并在提示中强制 `SKILL.md → 目标阶段切片 → 明确模板/Schema/门禁` 后，review 缺前置规格探针约 31 秒返回 `BLOCKED`；未读 README/`maintainer/`、未做外部调研、未伪造签署或证据，符合预期。
- 本轮实际模型证据为 4/9 阶段：frame、explore、intake 的产物 PASS，review 的正确阻断 PASS；其余六阶段仍是 `NOT_RUN`，不能宣称 Kimi 已完成九阶段全覆盖。15×9 提示包和确定性门禁只证明测试入口完整，不替代真实模型运行。
- 因此将最小加载、停止条件、耗时、产物数和门禁结果固化为无人值守执行合同。后续模型抽测优先选择一个可产生产物的阶段和一个必须阻断的阶段，不为“跑满矩阵”无控制消耗 Token。

## 5.4.2 体验回归：精准、稳定、快速优先

### 问题定级

5.4.1 对 Human-First 门禁和存量页面处置的修复有效，但 5.4.x 仍有一组发布级体验风险：

1. **P0 触发逃逸**：其他模型会在调用 Skill 前以“功能简单、需求明确”为由跳过。运行时正文无法修复一个发生在正文加载之前的问题；主触发合同必须写入 frontmatter description 和平台入口提示。
2. **阶段治理被误当执行清单**：九工作站虽然声明“不是瀑布”，但阶段表、产物表和门禁示例容易诱发补跑前序、逐站落盘和逐站校验。
3. **澄清正确但不够快**：旧的 L1/L2/L3 固定批次上限会把风险上限误读为默认轮次；直播对话过早展示 `UNK/DEC/YAML` 会增加理解成本。
4. **原型视觉治理既重又不确定**：所有高保真原型都要求先确认 `DEC-AESTHETIC-*` 会阻断存量小迭代；只有“保持一致”的泛化措辞又不足以阻止跨页面 token、密度、组件和骨架漂移。
5. **门禁诊断导致修复回合膨胀**：默认只返回第一条 finding 时，同一根因产生的几十条明细会迫使使用者反复运行；全量 JSON 又不适合人类阅读。

### 5.4.1 可复现基线

- 维护脚本：`test_v511_runtime_budget.py` 1.839 秒、`test_v540_stage_contracts.py` 18.897 秒、`test_v541_human_first_gate.py` 0.458 秒，均通过。脚本运行本身不是主要体验瓶颈。
- 历史模型证据：Kimi K3 intake 曾约 424 秒、约 60 KB；使用 allowlist 和精确阶段切片后，review 正确阻断约 31 秒。这证明上下文与目标范围比单个门禁脚本更影响总耗时。
- 独立 Codex 探针：在明确要求使用当前 Skill 时，5.4.1 对“明确小需求”“模糊早期想法”“存量原型小迭代”三题均能首答提供可用价值，分别做到零问题直接规格、一轮发散聚焦后只问一个问题、继承现有风格且不询问美学方向。因此 5.4.2 必须保留这些已正确行为，不能以重写框架的方式修复跨模型问题。
- 真实 PRD 门禁：企业约谈 PRD 产生 62 条 finding、15 个唯一根因码；full JSON 约 99,687 字符。5.4.1 默认 first 模式理论上最多需要 15 个根因修复回合。

以上独立 Agent 探针是单模型单次探索证据，不是用户满意度、跨模型通过或一般性性能提升证明。

### 5.4.2 决策

1. **触发前置**：frontmatter 和平台入口同时声明“需求、PRD、原型、竞品、存量系统的新增/修改/评审/反推/验收必须先调用”，并明确禁止以规模或清晰度跳过；负向调试任务仍不触发。
2. **直达目标**：阶段是路由地图，不是待办清单。明确任务不补前序文件；模糊任务先在首答完成“发散 → 推荐聚焦 → 深化”，再只问会改变范围的决策。
3. **对话与持久化分离**：直播对话只展示人类可理解的判断、选项和问题；跨会话、多人协作、审计或工具编译时才落 `SRC/ASM/UNK/DEC/YAML`。
4. **风险轮次预算**：明确小需求默认零轮；普通模糊需求最多两个阻断决策轮；安全、法规、金钱和强合规最多四轮。预算是上限，不是目标。
5. **视觉权威与视觉锁**：存量小迭代默认继承既有 HTML/截图；绿地内部工具可选择克制可逆默认；只有品牌化或方向会显著改变交付时才询问审美。跨页锁定 tokens、typography、shell、components、density 和 taboos。
6. **根因诊断**：CLI 默认 `--diagnostics roots`，每个唯一 finding code 展示一次并附重复数；JSON 保留全部明细，`first/summary/full` 继续兼容。
7. **里程碑门禁**：只在目标里程碑运行一次并修复后重跑，不随经过的工作站逐站运行。

### 已量化的候选结果

在同一企业约谈 PRD、同一仓库和同一 Python 环境下：

| 指标 | 5.4.1 基线 | 5.4.2 候选 | 结论 |
|---|---:|---:|---|
| finding 总数 | 62 | 62 | 机器诊断能力未减少 |
| 唯一根因码 | 15 | 15 | 根因覆盖保持 |
| 默认可读输出 | first，一次 1 个根因 | roots，一次 15 个根因 | 理论修复轮从最多 15 轮降为 1 轮 |
| 全量/默认输出字符 | JSON 99,687 | concise 3,696 | 默认阅读量减少约 96.3% |
| 默认根因覆盖率 | 1/15 | 15/15 | 6.7% → 100% |

这里的改进是诊断消费成本，不宣称静态检测计算时间显著下降；实测约 1 秒量级且差异没有统计意义。

### 发布评价合同

5.4.2 不能只凭结构测试声称“评价最高”。发布候选至少覆盖四类形态：明确小需求、模糊早期想法、存量原型小迭代、受监管复杂需求；每类固定相同输入、模型、设置和重复次数，记录：

- Skill 触发决定与跳过理由；
- 首个可用结果耗时；
- 澄清决策轮数；
- 不必要阶段数；
- 无依据扩范围/重设计数；
- 目标产物完成结果；
- 原型视觉锁一致率；
- 门禁修复轮数；
- 真实用户版本化评分。

跨模型正式结论仍需 DeepSeek、GLM、Codex 等实际 provider/model/client 运行证据。没有真实用户评分前，只能发布为“体验合同与已知回归通过”，不能宣传为已获得最高用户评价。

### 删除而非叠加

5.4.2 删除固定的 3/6/8 批澄清默认、删除所有高保真原型的强制美学暂停、删除重复的美学确认章节，并把 first finding 从默认改为显式选项。没有新增第十阶段、第二套 PRD、生成式门禁、自然语言关键词路由或独立视觉框架。

### Maintainer 收敛

用户指出维护与验证资产已经反客为主。审计基线为 84 个活跃文件、694,739 字节，公共 `check` 串行执行 45 项。5.4.2 采取以下处置：

- 删除 22 个历史 GitHub 矩阵、逐次运行证据、重复评分/比较工具、只重复上级说明的示例 README；再将 9 个版本专属重复测试合并为 `test_product_experience.py` 与 `test_runtime_resilience.py` 两个能力级套件，需要追溯时从 Git 历史读取，不占活跃树。
- 保留会影响当前发布结论的领域夹具、体验指标、确定性合同测试和版本状态；没有因瘦身降低运行时门禁覆盖。
- 公共 `check` 默认只跑 10 项高风险快速门禁；历史兼容与完整领域回归移入显式 `check --profile release`。
- 用预算防止回潮：`maintainer/` 最多 56 个文件、450,000 字节，默认快速检查最多 12 项。新增资产必须替换、合并或说明其独立发布决策价值。

候选树收敛为 55 个文件、约 402 KB。文件数减少 34.5%，体积减少约 40.8%，默认命令数减少 77.8%。这些数字描述维护面，不冒充用户任务耗时或模型质量提升。

### 候选新会话探针

三个互不共享对话历史的候选 Agent 只读当前 Skill 后执行固定输入：

- 明确小需求：直接给出企业约谈状态筛选的开发规则与 8 条验收，0 个澄清问题，没有稳定 ID、YAML 或阶段术语，符合预期。
- 存量原型小迭代：先读取列表、发起、详情三份 HTML，锁定跨页现有布局与组件，只准备增加行业下拉，不询问美学、不重设计，符合预期。
- 模糊早期想法首跑：虽然完成发散、推荐、深化和单一问题，但把当前 CRM 工作区的客户、合同、回款语义移植给了领域尚未确认的“运智管家”，判为上下文污染，不通过。
- 修复后同题复测：明确领域未知，不预设 CRM/物流/供应链；以条件分支提出风险雷达、业务过程异常、决策助手和响应闭环，推荐跨领域最小闭环，只问“业务场景＋用户＋决定”，通过。
- 真实企业约谈 PRD 门禁：0.907 秒产生 62 条完整 finding、15 个唯一根因，默认输出 15 个根因并压缩 47 条重复明细；退出码 2 正确表示产物仍被阻断。

以上四类探针只构成当前模型独立会话与确定性门禁的 `partial` 证据。DeepSeek、GLM 等匹配输入的重复运行和真实用户版本化评分仍为 `not_run`。
