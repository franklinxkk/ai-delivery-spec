# v5.4.0 设计记录：阶段工作站，而非更重的全链路框架

## 决策

在 5.3.3 的需求管理内核上增加九个“可进入/可停止/可续接”的工作站，但不升级为 v6，不增加第二套生命周期、第二套 CLI 或第二套门禁状态。

## 吸收的专家实践

- `frame → explore → intake → clarify → specify → review → baseline → change → acceptance` 的阶段矩阵。
- 问题简报、方案草图、假设、决策与需求简报作为可交接产物。
- 角色可以在所需阶段进入，目标产物完成即可离开。
- 跨会话续接必须保存前序产物和开放线程。

## 未直接照搬的部分及原因

1. 不用关键词脚本推断自然语言：它会把“不要写 PRD，只做澄清”误路由到 specify，也难以稳定支持多语言和否定语义。
2. 不要求每次运行 stage router：模型负责语义，工具只做确定性核验，避免新增 shell/转义/Token 成本。
3. 不增加独立 `stage_gate.py + stage_router.py`：合并为一个 `stage_contract.py`，并从现有公共 CLI 调用。
4. 不发明 `COMPLETE/NOT_READY`：继续使用 `PASS / REVIEW_COMPLETE_WITH_GAPS / BLOCKED_BY_P0_UNKNOWN / BLOCKED`。
5. 不为每阶段强制一份文件：frame/explore/clarify 默认各一份；假设和决策仅在治理需要时拆侧车；baseline 复用统一规格。
6. 不让 artifact resume 替代大项目 execution-state：前者保证交接完整性，后者保存 ID 切片、预算和运行检查点。
7. 不在 frame/explore 提前分配正式需求 ID：正式治理从 intake 开始，避免把脑暴选项误当批准需求。

## 关键不变量

- 一份统一 PRD/需求卡仍是人类与 Coding Agent 共用基线；Product Truth 严格按需。
- 用户语言、来源权威、稳定 ID、禁止推断、双向追溯和真实验收边界不回退。
- 任何角色都能从现有证据进入，但 review/baseline/change/acceptance 不得在缺少可消费规格时凭空继续。
- 早期假设是 GAP，不自动成为 P0；P0 只阻断已经到达且受影响的正式阶段。
- 静态门禁不证明业务正确、实现完成、浏览器行为或客户签署。

## 文件与运行成本

- 新增一个阶段参考、一个合并脚本、两个 schema、五个模板和两个聚合回归文件；不增加碎片夹具。
- 维护设计记录只在发布保障时读取，不进入普通项目上下文。
- 冻结巨型 `quality_gate.py` 的新功能增长；早期工作站语义集中在 `stage_contract.py`，公共 CLI 只路由，不复制规则。
- Schema 版本按结构演进，不为追随 Skill 版本机械批量改号；只有新增 intake 合同使用 5.4.0。
- 仓库发布文件必须 `< 200`；第三方运行包使用 allowlist，`maintainer/` 不随普通用户运行时下发。

## 发布前案例与模型证据边界

- 15 个固定 GitHub 案例用于验证跨领域需求形态，7 行业保障组合用于验证阶段与角色覆盖；两者共同提供广度证据，但不等同于所有行业已经获得领域专家签署。
- 15 个案例各绑定一个“一句话需求”生命周期探针，并覆盖全部九阶段。`review / baseline / change / acceptance` 缺少前序证据时，正确行为是阻断并返回最小前置材料，而不是伪造产物。
- 下一轮真实快照优先候选为 OpenAI Codex、Qwen Code、ERPNext、DataHub、OpenEMR 与 Keycloak，分别补齐 AI Agent 协作、制造 ERP、数据治理、医疗与 IAM 场景；只有完成固定提交、来源路径、义务与运行证据后才能进入正式案例目录。
- Grok-1 主要是模型权重与推理实现，不直接代表需求生命周期或 Agent 工作流，不能为了品牌覆盖强行纳入。
- 跨模型测试必须记录真实 `provider / model_id / client_version / settings / run_at / output_ref`；生成测试包不等于模型已经通过，禁止使用共享、泄露或来源不明的凭据。

## Claude 系统测评的处置

本轮接受并落地：

- `review-record` 增加 `architecture / delivery / cross_functional` 类型、`required_review_types` 和逐角色 `sign_offs`；完成态不再只凭“没有 finding”通过。
- 新增“需求交付/技术负责人”使用者角色和离线需求池汇总，汇总优先级、复杂度带、依赖与迭代归属，但不接管 Sprint、人员、工期和容量决策。
- 在既有工具适配页增加 Jira/Linear/Azure DevOps/TAPD/禅道的索引映射，外部状态只写 `external_milestones`，不能覆盖统一需求基线。
- 独立区分 `architecture` 与 `engineering` 评审；补充紧急变更的临时授权、最小止损、回滚与补审规则；明确 Skill 使用者角色与 PRD `ROLE-*` 业务角色不是同一概念。

明确不扩张：

- 不增加 launch/monitor/operations 第十阶段。验收结论交给外部发布系统，线上反馈以新 `SRC-*` 回到 intake，或对既有基线创建 `CHG-*`。这是需求闭环交接，不是研发/运营管理。
- 暂不增加独立 ADR 模板；架构签署和决策继续复用 `decision-record` 与 review sign-off，避免文件膨胀。
- 暂不把 junior escalation、双语一致性或到期提醒扩成全局重型对象；先通过责任边界、P0 `blocks_stage` 和结构化评审阻断，后续只在真实逃逸案例证明需要时升级。

模型越强，越要删减“教模型如何思考”的重复 prose；稳定 ID、共享状态、证据、领域不变量和确定性门禁则继续保留。后续用目标模型对“完整段落 vs 两行锚点+门禁”做 A/B，行为无差异的推理提示删除，不凭厂商宣传机械瘦身。

## Kimi K3 受控复测与成本结论

- 仅使用本机 Kimi Code 的官方 OAuth 会话和运行时返回的 `kimi-code/k3`；用户在对话中提供的 Token 未使用、未写入任何文件，也不作为证据。
- 仓库工作副本首次抽测 frame / explore / intake：三个阶段的行为和独立门禁均通过，但 intake 约 424 秒、响应约 60 KB，说明“产物正确”不能掩盖加载与分析成本失控。
- 改用 101 文件 allowlist 运行包，并在提示中强制 `SKILL.md → 目标阶段切片 → 明确模板/Schema/门禁` 后，review 缺前置规格探针约 31 秒返回 `BLOCKED`；未读 README/`maintainer/`、未做外部调研、未伪造签署或证据，符合预期。
- 本轮实际模型证据为 4/9 阶段：frame、explore、intake 的产物 PASS，review 的正确阻断 PASS；其余六阶段仍是 `NOT_RUN`，不能宣称 Kimi 已完成九阶段全覆盖。15×9 提示包和确定性门禁只证明测试入口完整，不替代真实模型运行。
- 因此将最小加载、停止条件、耗时、产物数和门禁结果固化为无人值守执行合同。后续模型抽测优先选择一个可产生产物的阶段和一个必须阻断的阶段，不为“跑满矩阵”无控制消耗 Token。
