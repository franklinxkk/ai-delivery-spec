# 发布前实测

发布候选固定文件指纹，先修已证实问题，再对受影响行为复验。只重复因修改而失效的证据。版本号、运行包、源码快照和结果必须对应；未获授权不发布。

每次准备向 GitHub 提交封板版本、打发布标签或替换 Release，维护者在本地完成本轮工程回归、三模型同题对照及产物交叉冷读，记录明确的发布结论。普通开发提交和使用本 Skill 写需求沿用原有流程。

## 变更与用例一起维护

逐项对照上次发行以来改变的行为，说明哪个合法操作还应成功、哪种错误必须因什么原因被拒绝、失败后原数据和下游结果如何核对。已有用例能观察到相应结果就复用。遇到本次新增规则、旧用例仍会放过的错误或失效的旧断言，就补充或替换用例。对修复尽量保留同一案例修前失败、修后通过的证据。文件结构、命令成功、真实操作、正式授权分别验明。跳过的用例写明缺的是哪种环境及其影响。

## TRACE 自评

按 TRACE 五维组织下表的本地证据，采用公开维度及本地实测结果。发布时复核平台版本、来源和日期。SkillHub 另有内容合规、科恩实验室漏洞扫描、云鼎实验室 AI 安全评估三个上架审核环节；只有平台对相应版本的报告才记为平台实评。[腾讯云 TRACE 说明](https://developer.cloud.tencent.com/techpedia/2618) · [SkillHub 平台说明](https://skillhub.cn/)

| 维度 | 本地观察 | 不能据此宣称 |
|---|---|---|
| T 可信任度 | 无关权限/外传、外部材料冒充指令、私有材料泄漏；离线核心能力和中英入口 | 静态抽查等于双实验室安全认证；所有国内网络都可用 |
| R 可靠性 | 实际入口、边界/反例、可操作错误、提取后运行包；新旧合同兼容 | 测试数量等于业务正确或任意语义可判定 |
| A 适用性 | 主流行业、中英输入、阶段与角色、微改及非需求负例；四快捷意图 | 模拟路由等于宿主实际隐式命中率 |
| C 规范性 | README 首屏复述和首次行动；按需导航、链接、模板和示例一致 | 模型表示愿意使用等于真人转化率 |
| E 有效性 | 新任务实际产物，接收者按模块复述/造数，跨产物一致与正反结果 | 合成案例等于真实项目返工减少或生产验收 |

先冻结适用义务及排除理由，分别报已检查覆盖率与已检查项满足率，失败、未查、不适用单列；没有检查时满足率为未计算。权重仅在事先有依据时使用，否则按项计数。关键未查不能被平均分掩盖。每维写观察、证据位置、问题处置和未测范围；需要评分时说明自定标尺，不能捏造官方分值。严重授权错误、关键规则冲突或关键流程不可用不能被平均分掩盖。已核实平台评分可用于介绍，但标明对应版本和核实日期。

## 模型冷启动对比

基准组固定为 GPT-6.2 Sol、GPT-6.2 Astra 和 DeepSeek Flash 系列。每次向 GitHub 提交封板版本前核对宿主可用模型与厂商更新记录。旧别名重定向、型号退役或出现后继型号时，告诉维护者请求名、实际型号及变化；新型号的效果单独标注。每个模型独立完成带 Skill / 不带 Skill 两次首答，同一组内使用相同的业务材料、工具权限、推理设置、交付要求和预先冻结的判据，带 Skill 组只额外收到本候选的相关内容。跨宿主时如实记录能力差异。每轮至少覆盖两个不同任务场景，纳入当版风险；若声称原型可操作，应实际从使用入口走到结果。缺模型、单臂或独立接收记录时保留缺口，暂缓封板。

1. 选同一候选包和同一任务集。列明行业、阶段、角色、语言和交付类型的覆盖单元及正反预期，区分计划、产出、独立核对与通过，说明未覆盖组合。跨阶段结论须有同一需求贯穿交付、变更及验收的链，不能用独立短题拼成全流程。预先独立记录正确结果和重要错误，参与模型只拿任务/来源，不拿判分答案。
2. 每模型开无历史上下文会话；记录实际模型、输入、读取文件、命令和产物。先只给 README 首屏做用途/受众/下一步复述，再按任务读取 Skill。该环节叫首屏冷读模拟，不声称实测真人十秒。
3. 要求生成实际交付物并执行可用检查，不接受只描述“我会怎么做”。工具报错、配额或环境失败保留原记录，不算产品通过；反例须因目标约束被拒绝，其他报错不能冒充通过。修正前保留实际文件和日志，不只保留哈希；作者检查、独立接收和父代理补测分别归属。
4. 每份首答交给另一种模型冷读，隐藏作者与分组。接收方先只看交付件，记录能实现或测试什么、缺什么，保留首次判断，再给原始来源与判据核对；来源本属约定交付包时随包提供。必要时在浏览器实际操作。修复另记。记录关键错误和各组实际优势，不能用平均分抵消关键失败。
5. 比较须猜业务选择、无依据扩展、关键漏项、跨产物冲突、可执行验收以及查找成本。不同模型同犯一错仍然是错。没有可靠计量时不报告耗时/token收益。

## 真人与项目效果

改生成/自检机制时，用普通任务口吻和原始材料做前后对照，不在任务里泄露边界清单或要求“专测某个缺陷”。两组用冻结技能、相同输入和环境，作者无历史讨论；真实缺决定可提出，接收者不要求它猜指定答案。首次作者交付前可自检，交付后立即封存文件；接收者先读约定交付包并冻结疑问，再给来源核对忠实性；随后给一次普通局部变更，检查旧行为和数据是否保留。

逐根因记录：首次交付违背已定规则、无授权扩展、关键遗漏/歧义、视觉或交互阻断、修订引入的回退、实际需用户澄清的业务选择。作者自检发现与独立接收后发现分开；环境失败单列。保留首份和修订份，比较同范围结果，少量案例只能说明该实验观察，不能换算普遍成功率、真人时间或返工收益。

有授权且有同口径记录时，记录真实项目首次交接后的澄清轮次、需求原因返工、实现缺陷及环境失败，保留分母和时期。无可比前测，不计算提升百分比。只有合成或模型数据时明确“该指标未测”，不因此杜撰真实业务数据，也不把日常任务升级成测评项目。

## 封板记录

编号文本合题可运行 `python maintainer/tools/check_release_evidence.py --candidate <候选ZIP> --evidence-dir <私有证据目录>` 核对候选、输入、组别与回读记录。原生 Word、可操作 HTML、多文件或无编号文稿按同一对照要求，在私有索引中逐场景关联候选指纹、首份原件、各自运行来源及跨模型冷读记录，由维护者直接打开原件复核。两种形式均需看实物后裁决；相同答案可用各自的独立运行记录佐证。工程 `check --profile release` 另行运行。日常 PR 无需上传答卷、凭据或客户材料。

ClawHub 验收按准确版本和发布者核查用途与能力、指令授权、安装来源、环境与凭据、持久化和权限。分别保存 A.I.G、SkillSpector、ClawScan 已返回的状态与覆盖范围，核对汇总数、导出明细数及不同 finding ID 数。数目不一致时先取官方 verify 的原始 scannerReports（如有留存），再按实际调用与版本分辨成立、误报、证据不足。对依赖公告按安装版本查受影响区间。自己运行的对照、作者导出的旧版报告、平台对待发布版本的扫描分别登记。[ClawHub 审计方法](https://docs.openclaw.ai/clawhub/security-audits) · [公开核验接口](https://github.com/openclaw/clawhub/blob/main/docs/http-api.md)

记录本次修复、受影响回归、模型产物与接收结论、TRACE 观察、已知阻塞与非阻塞限制、运行包/源码指纹。核心未测或失败项仍影响交付时暂不封板；明确边界内证据充分即停止，不追求穷举所有组合。
